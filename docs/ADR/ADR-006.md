# ADR-006: Cancellation as a Soft-Status Transition

**Status:** Accepted
**Date:** 2026-08-01

## Context

`DELETE /appointments/{id}` needs to cancel an appointment. The implementation plan originally left open whether this is a hard delete or a soft-status change to `CANCELLED` ("documented per implementation"). The API contract (Section 10) already specifies that a second cancellation attempt on the same appointment returns `409 Conflict` — which requires the appointment record to still exist and be inspectable after the first cancellation.

## Decision

`DELETE /appointments/{id}` performs a soft-status transition: `status` is set to `CANCELLED` on the existing row. The row is never physically deleted by this endpoint.

## Rationale

- The `status` enum (`SCHEDULED`, `CANCELLED`, `COMPLETED`) already exists in the schema (Section 11) specifically to represent appointment lifecycle state; a hard delete would make that enum value unreachable in practice.
- The `409 Conflict` behavior specified for "already cancelled" is only implementable if the row and its prior status remain queryable — a hard-deleted row has nothing to check against.
- Preserves booking history for a scheduling domain where "was this ever booked" has obvious value, without requiring a separate audit/history table (explicitly out of scope per Section 4).
- Consistent with the `ON DELETE RESTRICT` FK strategy already chosen for `appointments` — the codebase already leans toward preserving rows rather than cascading/hard-deleting.

## Alternatives Considered

- **Hard delete** — simpler query logic, but destroys history and breaks the `409`-on-repeat-cancel contract; rejected.
- **Leave undecided until implementation** — the original wording; rejected because it risks the `DELETE` endpoint and its `409` behavior being implemented inconsistently, or discovered as a contradiction mid-implementation rather than resolved up front.

## Consequences

- `GET /appointments` and `GET /appointments/{id}` must be able to return `CANCELLED` appointments (they are not deleted from the table); callers filter by `status` if they want to exclude them.
- No separate audit/history table is introduced — the appointment row's own `status` field is the only cancellation record kept.
