# ADR-001: Use FastAPI as the web framework

**Status:** Accepted
**Date:** 2026-08-01

## Context

Need a Python web framework to build a small backend service within a one-week, ~14–16h budget, with strong typing, automatic request validation, and easy testability.

## Decision

Use FastAPI with Pydantic for request/response schemas.

## Rationale

- Native Pydantic integration gives request validation and OpenAPI docs for free — no hand-written validation boilerplate.
- Async-first, but works equally well synchronously; doesn't force a concurrency model decision this project doesn't need to make.
- `TestClient` (via `httpx`) makes integration testing straightforward without spinning up a real server.
- Widely used in modern Python backends, so the choice itself isn't a talking point — the interesting decisions are in what's built _on top_ of it (service/repository layering, transaction handling).

## Alternatives Considered

- **Flask** — more manual wiring for validation/OpenAPI; would cost time better spent on business logic.
- **Django REST Framework** — brings an ORM, admin site, and app structure heavier than this domain needs; would fight the intentionally small scope.

## Consequences

- Pydantic schemas become the API contract boundary (kept separate from SQLAlchemy models, see folder structure in the implementation plan).
- Framework-specific code is confined to `app/api/` and `app/core/middleware.py`; the service layer stays framework-agnostic and unit-testable without FastAPI running.

## Amendment (2026-08-01) — Sync vs. Async Confirmed

This project uses FastAPI's synchronous request-handling path with a synchronous SQLAlchemy 2 engine/session (`psycopg`), not `asyncpg`/async SQLAlchemy. This resolves the concurrency-model question left open above in favor of the simpler option: sync `SELECT ... FOR UPDATE` transaction handling, session management, and test fixtures (`TestClient`, plain `pytest`) are all more straightforward than their async equivalents, and nothing in this project's scale (single instance, local Docker Compose, no real concurrent load target) benefits from async I/O. `docs/architecture.md`'s container diagram is updated accordingly.
