# ADR-002: Introduce a Service Layer between API and Repository

**Status:** Accepted
**Date:** 2026-08-01

## Context

The booking flow has multiple validation and assignment steps (vehicle, service type, technician, bay, overlap, transaction) that are pure business logic, independent of HTTP. Without a dedicated layer, this logic tends to leak into route handlers, becoming hard to unit test and easy to duplicate.

## Decision

Introduce a `services/` layer (e.g. `BookingService`) that sits between the API layer and the repositories, and owns all business rules and the transaction boundary for the booking use case.

## Rationale

- Route handlers stay thin: parse request → call service → serialize response. No business logic to review there.
- `BookingService` can be unit tested with fake/mocked repositories, with zero HTTP or database involved — this is what makes the "booking success / overlap / no technician / no bay" test suite fast and reliable.
- Centralizing the transaction boundary in the service (rather than the repository or the route) means exactly one place enforces "all these checks + the insert happen atomically or not at all."
- This mirrors how the same domain logic would be reused if this API grew a second entry point (e.g. an internal admin tool, a batch import) without duplicating booking rules.

## Alternatives Considered

- **Fat models / active record style** — business logic on the ORM models themselves; rejected because it couples business rules to persistence, making them harder to test in isolation and harder to reason about transaction boundaries.
- **Logic directly in route handlers** — fastest to write, but untestable without spinning up the whole app/DB, and duplicates easily once there's more than one entry point.

## Consequences

- One extra layer of indirection (API → Service → Repository) for what could be a 3-line CRUD operation in some cases (e.g. `GET /appointments/{id}`) — accepted as the cost of a consistent, predictable architecture across both simple and complex endpoints.
