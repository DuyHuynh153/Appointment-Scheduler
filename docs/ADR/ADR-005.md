# ADR-005: Use `SELECT FOR UPDATE` for booking concurrency control

**Status:** Accepted
**Date:** 2026-08-01

## Context

Two concurrent requests could attempt to book the same technician or bay for overlapping time windows. Without explicit concurrency control, both requests could pass the overlap check before either commits, resulting in a double-booking.

## Decision

Within the single transaction that performs the booking, re-check candidate technician/bay availability using `SELECT ... FOR UPDATE` (row-level locking) immediately before the overlap check and insert. This is the only concurrency-control mechanism implemented.

## Rationale

- `SELECT FOR UPDATE` closes the classic check-then-act race window: the second concurrent transaction blocks on the lock until the first commits or rolls back, then re-evaluates availability against up-to-date data.
- It's straightforward to implement, test, and explain, and requires no schema changes beyond what's already planned.
- It correctly handles the actual invariant needed here ("no two appointments overlap for the same technician/bay"), which is a range-overlap condition, not a simple equality — a naive unique constraint could not express this directly.

## Alternatives Considered (and explicitly not implemented)

- **PostgreSQL `EXCLUDE USING gist` constraint** on `(technician_id, tstzrange(start_time, end_time))` — the more Postgres-idiomatic, schema-enforced solution, since it makes the invariant impossible to violate regardless of application code path (including out-of-band scripts). Not implemented in this assessment to keep the migration/index surface small within the time budget; documented here as the clear next step if this went to production, rather than silently omitted.
- **Optimistic locking / retry-on-conflict** — adds application-level retry complexity for a range-overlap check that doesn't map cleanly onto a simple version/unique-column conflict; rejected as more complex than `SELECT FOR UPDATE` for no added correctness benefit at this scale.
- **`SERIALIZABLE` isolation level for the whole transaction** — would also prevent the anomaly, but at the cost of application-wide retry-on-serialization-failure handling and reduced throughput; row-level locking scoped to just the contested rows is a more targeted fix for this specific invariant.

## Consequences

- Correctness depends on every write path going through `BookingService` (the only place the lock + overlap check happen); any future direct-SQL or admin-tool write path would need the same discipline or the `EXCLUDE` constraint from the future-improvement list.
- Under high contention on the same technician/bay, requests serialize (block on the row lock) rather than fail fast — acceptable at this scale; would be revisited if it became a bottleneck.

## Amendment (2026-08-01) — Vehicle Included in Row-Locking

The no-overlap invariant also applies to the vehicle (Section 9 of the implementation plan: a vehicle cannot be serviced twice concurrently). The original wording above only mentioned technician/bay rows. To close the same check-then-act race window for the third resource, the candidate **vehicle** row is also re-checked with `SELECT ... FOR UPDATE` in the same transaction, immediately before the overlap check and insert — using the identical mechanism already used for technician/bay, rather than leaving vehicle overlap protected only by transaction isolation. `appointments(vehicle_id, start_time, end_time)` gets the same composite index as the technician/bay overlap lookups to keep this query cheap.
