# ADR-003: Correlation ID and Request ID as distinct concepts

**Status:** Accepted
**Date:** 2026-08-01

## Context

The system is currently a single monolithic service, but request tracing conventions decided now shape how easy it is to add tracing across service boundaries later, without breaking existing clients.

## Decision

Introduce two distinct identifiers on every request:

- `correlation_id` — read from the incoming `X-Correlation-ID` header if present, otherwise generated. Represents a logical call chain and is expected to be stable across multiple hops if this system is later split into multiple services.
- `request_id` — always generated fresh per request, identifying this specific request/response, even on client retries of the "same" logical call.

Both are included in every structured log line; `correlation_id` is also echoed back in the response header.

## Rationale

- Today it's a monolith, but the API contract is kept ready for future decomposition into multiple services: introducing `X-Correlation-ID` now means request tracing stays consistent across service boundaries later without changing clients.
- Distinguishing `request_id` from `correlation_id` avoids conflating "one client call" with "one attempt at that call" — useful once retries or gateway-level redelivery exist, and makes log correlation unambiguous even now (e.g. distinguishing two attempts under the same correlation id).
- Cost is a single extra middleware and two extra log fields — negligible for a large gain in future-proofing and log usability.

## Alternatives Considered

- **Correlation ID only, no request ID** — simpler, but conflates "this call" with "this attempt," making it harder to separate retries from distinct logical operations in logs.
- **No correlation ID at all (rely on framework/reverse-proxy logs)** — rejected because it pushes the concern outside the service, and doesn't demonstrate the tracing-readiness this decision is meant to signal.

## Consequences

- Every response carries an `X-Correlation-ID` header, so clients (or a future gateway) can propagate it.
- Every log line is joinable by either id, which will matter more once there is more than one service to correlate across.
